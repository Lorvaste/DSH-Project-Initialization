# 完善与变更（polish）

目标：有中生优——从已有初稿/项目出发，完善或变更方案，全程显式对齐。对应 plan.md「项目进行中」路径。

## 双子场景入口

进入场景后，询问用户（一次一个问题）：

- **① 初版方案完善**：用户提交一份初版方案，需要完善
- **② 修改方案与目标**：进行中的项目需要修改方案与目标

---

## 子场景 ①：初版方案完善

### 步骤

0. **工作区准备**：确认工作区目录并向用户确认（"确认是 <路径> 吗？"）
   - 无 git 仓库则 `git init -b main` + 配置本地身份（user.name/email，项目级）
   - 闸门：工作区确认 + git 就绪 → 进入下一步
1. **提交**：用户提交初版方案（粘贴文本或文件路径）
2. **结构化理解**：AI 把方案重述为四类规格（功能 F-xx / 细节 D-xx / 范围 R-xx / 实现 I-xx）+ 功能域（MOD-xx）归属
3. **核对理解**：用户确认 AI 的重述（复述确认——理解偏的防错闸门）
4. **遍历性验证**（七维度，见本文档内联清单，非引用外部 skill）：AI 检查方案——逻辑自洽 / 覆盖完整（四层规格缺层）/ 遗漏（结合领域模板：输入/异常/边界/数据/环境；**场景含实体/硬件时追加：供电/环境范围/失效模式/校准/通信/安全**）/ 可验证性 / 歧义性 / 依赖闭环 / 数量合理性
   - 按维度报告检查过程（可审计），不只给问题清单
   - 输出问题清单 → 用户确认 → 逐项补充（一次一问）→ **影响面复验**（只复验受影响条目）
   - 循环至无问题（用户可随时结束，以用户确定完成为准）
   - **通过标准闸门**（全部满足才进入成档）：四层规格全覆盖 / 0 矛盾 / 0 歧义 / 100% 可验证 / 每条可回溯到用户目标 / 领域模板全部过检
5. **成档**：逐条确认（已确认/待定/驳回，未确认条目不进 spec）→ 生成 **Reference/spec.md 初版终稿（v1.0）**，结构如下（自包含，不依赖其他场景 skill）：

```markdown
# spec.md — 项目规格（vX.Y 冻结）

## 元信息
项目名 / 场景类型（纯软件·纯实体·复合）/ 体量档位（浅·中·深）/
冻结版本 / 冻结日期 / 确认方式（AI 复述 + 用户逐条确认）

## 0. 功能域清单（用户理解，问答④确认）
| 域 ID | 功能域 | 说明 | 关联规格条目 |
| MOD-01 | ... | ... | F-01, D-01 |

## 1. 项目概述（想做什么）
一句话定位 + 目标价值 + 核心用户/用途

## 2. 功能规格（做什么）
| ID | 功能 | 状态 |
（不设优先级；验收归场景外会话，spec 为纯需求描述）

## 3. 细节规格（参数·边界·界面）
| ID | 关联功能 | 细节 | 边界/异常 | 状态 |

## 4. 范围声明（不做什么）
| ID | 排除项 | 原因 | 状态 |

## 5. 实现约束（技术栈·偏好）
| ID | 约束 | 说明 | 状态 |

## 6. 变更记录
| 版本 | 日期 | 变更 | 原因 | 确认 |
```

- 条目编号：F/D/R/I 前缀 + 序号（追溯锚点）；状态冻结时全部「已确认」

6. **可选任务拆分**：按功能域生成 Reference/tasks.md 初稿（自包含结构）：

```markdown
# tasks.md — 任务拆分（初稿）

## 元信息
关联规格版本：vX.Y

## 功能域（用户理解，问答④确认）
| 域 ID | 功能域 | 说明 | 关联规格条目 |
| MOD-01 | ... | ... | F-01, D-01 |

## 任务清单（按功能域组织）
### MOD-01 ...
| ID | 任务 | 关联规格 | 落点 | 依赖 | 状态 |
| MOD-01-T01 | ... | F-01 | Frontend/ | - | 待办 |
```

- 域 ID：`MOD-xx`；任务 ID：`MOD-xx-Tyy`；任务粒度由用户决定
- **落点列**：任务产物归属目录（复合项目必填——追溯矩阵"需求↔任务↔产物↔验收"的产物环节）
- **tasks.md 由用户确认后**才推送（确认闸门：用户过目任务清单）
- 任务拆分确认后**询问是否启用域开发骨架**（按 Rules.md 4.8：启用则生成 Reference/domains/MOD-xx/ 五件套，不启用则记录到 tasks.md 元信息与 Progress.md 双处）

7. **推送**：git add/commit（**commit 信息含版本号，用英文**，如 `docs: spec v1.0 initial freeze`——Rules §1 git 提交信息用英文）/push（push 可选，沙箱拦截时引导权限升级）
8. **场景结束**：交付总结（spec 版本 v1.0、任务数、远端状态）

### 输入要求

- 用户提交的初版方案可以是任意格式（草稿/清单/口头描述），AI 负责结构化
- 若方案信息不足以成档（四类规格严重缺层），先补全再成档

## 子场景 ②：修改方案与目标（进行中项目）

### 步骤

1. **确认现场**：确认工作区（向用户确认"是 <路径> 吗？"）+ git 状态与远端链接；目录无仓库时参照①工作区准备兜底（git init + 身份配置）
   - 闸门：工作区确认 + git 状态确认 → 进入下一步
2. **理解文档**：读取现有 Reference/spec.md、Reference/tasks.md、plan.md、Progress.md → AI 复述理解 → 用户核对
3. **变更访谈**：用户提出修改需求（新方案/新目标）
   - 聚焦变更范围：改什么（功能/细节/范围/实现）、影响哪些现有条目、新增什么
   - 一次一问；以用户确定完成为准
   - **压缩版遍历检查**：新需求过检——输入/异常/边界/数据/环境 + 可验证性 + 歧义性 + 依赖闭环；**按维度报告检查过程（可审计，同子场景①）**；新需求与现有 F/R/D/I 条目冲突即触发裁决（先裁决再更新，不自行取舍）
4. **变更确认闸门（场景灵魂：先等等，让用户确认一下）**：
   - AI 汇总变更方案：新版本号 / 新增·修改·删除条目清单 / 新增功能域（如有）/ 受影响任务
   - 用户逐项确认（已确认/待定/驳回）→ 驳回项重新澄清 → **确认项才写入 spec**
5. **更新 spec（变更管理核心）**：
   - **版本递增与同步**：vX.Y → vX.(Y+1)；同步更新 spec 文件头 + 元信息「冻结版本」「冻结日期」+ tasks.md 元信息「关联规格版本」（追溯链不断裂）；主版本 X 仅在结构性重写时递增
   - **变更记录显式化**：spec 变更记录表新增一行（版本/日期/变更/原因/确认）
   - **受影响条目标记**：被修改的 F/D/R/I 条目标注（状态列注明「vX.(Y+1) 修改」）
   - **新增条目标记**：新增 F/D/R/I 条目标注（状态列注明「vX.(Y+1) 新增」），与修改标注区分
   - **新增条目**：新需求按编号体系追加（F-xx/D-xx/R-xx/I-xx）
     - **归属规则**：扩展既有条目能力 → 修改原条目并标注；全新能力 → 追加新条目；分类不确定 → 访谈中请用户拍板
   - **新增功能域**：新需求不属于现有功能域时新增 `MOD-xx`（编号续接），登记 spec §0 功能域清单与 tasks.md 功能域表——**功能域集合可扩展**
   - **删除/降级条目**：条目保留、状态列标「已删除/已降级（vX.Y）」，变更记录写明原因，不静默删除
6. **更新 tasks**：受影响任务标注（新增/修改/作废）；新增功能域按 MOD-xx 组织新任务段；功能域集合可扩展；**同步 Structure.md**（功能域表/结构树登记新域）；**若项目已启用域开发骨架**：同步受影响域的 `Reference/domains/MOD-xx/`（README 关联规格条目、plan 任务清单、Progress 状态）；新增功能域若用户要启用域骨架则按 Rules.md 4.8 生成
7. **推送前最终复核**：交付总结（新版本号、变更条目数、受影响任务数）→ **用户确认** → commit（信息含版本号，用英文，如 `docs: spec v1.1: budget alert + CSV export`）+ push（可选，沙箱拦截引导升级）
   - **可选产物对照**：用户需要时，AI 读取代码/文件对照更新后的 spec 生成偏差清单（符合/偏离/缺失）→ 用户确认 → 记录到 Progress.md（偏差涉及结构时按 Rules 4.6 追加）
8. **场景结束**

> 变更管理准则 = 步骤 5 规则 + 红旗表 + 刚性清单（见下），此处不重复列示。

---

## 准则（内联自包含，与 from-scratch 五组准则同源）

- **提问准则**：一次一问；带选项/示例；不诱导；不评判
- **记录准则**：每个回答显式记录；隐式假设逼出；矛盾检测请用户裁决
- **收敛准则**：AI 不得为问而问；以用户确定完成为准
- **冻结准则**：复述必须是结构化理解；未确认条目不进 spec
- **角色准则**：AI 是引导者不是决策者；用户是唯一权威；全程可回溯

## 状态记录

- 流程状态写入 Progress.md（workspace-check / doc-align / change-interview / spec-update / tasks-update / push / done）
- 任意状态可回退（用户说"回到某步"即回退）
- 闸门失败：回本步重做，可显式跳过（记录）

## 防漂移红旗表（Red Flags——这些想法意味着 STOP）

| 合理化念头 | 必须改为 |
|---|---|
| "理解过文档了，不用再核对" | 复述核对是刚性的——先等等，让用户确认一下 |
| "变更很小，不用升版本/不用记录" | 版本递增 + 变更记录显式化，禁止静默漂移 |
| "这条应该不影响其他条目" | 遍历受影响条目，逐条确认影响范围 |
| "用户没反对就是同意" | 沉默≠同意，必须显式确认 |
| "新目标和旧规格冲突，我自己判断" | 冲突先请用户裁决，不自行取舍 |

## 规则分级与优先级

- **刚性（Rigid，必须执行）**：复述核对 / **变更确认闸门** / spec 版本递增+同步+变更记录 / 受影响条目标记 / 新增条目与新增功能域登记 / 删除降级显式记录 / 冲突先裁决
- **弹性（Flexible，适配原则）**：变更访谈深度（以用户确定完成为准）/ 措辞方式
- **优先级链**：用户拍板 > 全局规则 > 域内规则 > 场景规则（完整链见 Rules.md 0.1）

## 工程准则

- **副作用显式管理**：每次变更检查影响面——受影响规格条目/任务/文档全部显式更新或标注，不遗漏
- **先查证，不假设**：以现有文档（spec/plan/Progress）为准，拿不准先读再问
- **三次失败协议**：失败路径 ① 诊断修复 → ② 换方案（不重复同一操作）→ ③ 重新思考 → 3 次后求助用户
