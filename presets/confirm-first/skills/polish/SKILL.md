# 完善与变更（polish）

目标：有中生优——从已有初稿/项目出发，完善或变更方案，全程显式对齐。对应 plan.md「项目进行中」路径。

## 双子场景入口

进入场景后，询问用户（一次一个问题）：

- **① 初版方案完善**：用户提交一份初版方案，需要完善
- **② 修改方案与目标**：进行中的项目需要修改方案与目标

---

## 子场景 ①：初版方案完善

### 步骤

1. **提交**：用户提交初版方案（粘贴文本或文件路径）
2. **结构化理解**：AI 把方案重述为四类规格（功能 F-xx / 细节 D-xx / 范围 R-xx / 实现 I-xx）+ 功能域（MOD-xx）归属
3. **核对理解**：用户确认 AI 的重述（复述确认——理解偏的防错闸门）
4. **遍历性验证**（七维度，同 interview skill ⑤）：AI 检查方案——逻辑自洽 / 覆盖完整（四层规格缺层）/ 遗漏（结合领域模板：输入/异常/边界/数据/环境）/ 可验证性 / 歧义性 / 依赖闭环 / 数量合理性
   - 按维度报告检查过程（可审计），不只给问题清单
   - 输出问题清单 → 用户确认 → 逐项补充（一次一问）→ **影响面复验**（只复验受影响条目）
   - 循环至无问题（用户可随时结束，以用户确定完成为准）
5. **成档**：复用 from-scratch 的 freeze 成档逻辑——逐条确认（已确认/待定/驳回）→ 生成 Reference/spec.md 初版终稿（F/D/R/I 编号、纯需求描述、变更记录）
6. **可选任务拆分**：复用 task-split 逻辑——按功能域生成 Reference/tasks.md 初稿（MOD-xx-Tyy）
7. **推送**：git add/commit/push（push 可选，沙箱拦截时引导权限升级）

### 输入要求

- 用户提交的初版方案可以是任意格式（草稿/清单/口头描述），AI 负责结构化
- 若方案信息不足以成档（四类规格严重缺层），先补全再成档

---

## 子场景 ②：修改方案与目标（进行中项目）

### 步骤

1. **确认现场**：确认工作区 + git 状态与远端链接
2. **理解文档**：读取现有 spec.md/plan.md/Progress.md/tasks.md → AI 复述理解 → 用户核对
3. **变更访谈**：用户提出修改需求（新方案/新目标）
   - 聚焦变更范围：改什么（功能/细节/范围/实现）、影响哪些现有条目、新增什么
   - 一次一问；以用户确定完成为准
4. **更新 spec（变更管理核心）**：
   - **版本递增**：vX.Y → vX.(Y+1)
   - **变更记录显式化**：spec 变更记录表新增一行（版本/日期/变更/原因/确认）
   - **受影响条目标记**：被修改的 F/D/R/I 条目标注变更（如状态列注明「vX.(Y+1 修改」）
   - **新增条目**：新需求按编号体系追加（F-xx/D-xx/R-xx/I-xx）
   - **删除/降级条目**：显式记录原因，不静默删除
5. **更新 tasks**：受影响任务标注（新增/修改/作废），按功能域组织不变
6. **推送**：commit + push（可选，沙箱拦截引导升级）
7. **场景结束**：交付总结（新版本号、变更条目数、受影响任务数）

### 变更管理准则

- **禁止静默漂移**：任何变更必须落到 spec 变更记录
- 文档是唯一权威：产物与文档冲突时以文档为准并记录偏差
- 用户提出的新目标若与现有规格冲突，先裁决再更新（不自行取舍）

## 准则（复用 from-scratch 五组准则）

- **提问准则**：一次一问；带选项/示例；不诱导；不评判
- **记录准则**：每个回答显式记录；隐式假设逼出；矛盾检测请用户裁决
- **收敛准则**：AI 不得为问而问；以用户确定完成为准
- **冻结准则**：复述必须是结构化理解；未确认条目不进 spec
- **角色准则**：AI 是引导者不是决策者；用户是唯一权威；全程可回溯

## 状态记录

- 流程状态写入 Progress.md（workspace-check / doc-align / change-interview / spec-update / tasks-update / push / done）
- 任意状态可回退（用户说"回到某步"即回退）
- 闸门失败：回本步重做，可显式跳过（记录）

## 防漂移红旗表（Red Flags——这些想法意味着 STOP）

| 合理化念头 | 必须改为 |
|---|---|
| "理解过文档了，不用再核对" | 复述核对是刚性的——先等等，让用户确认一下 |
| "变更很小，不用升版本/不用记录" | 版本递增 + 变更记录显式化，禁止静默漂移 |
| "这条应该不影响其他条目" | 遍历受影响条目，逐条确认影响范围 |
| "用户没反对就是同意" | 沉默≠同意，必须显式确认 |
| "新目标和旧规格冲突，我自己判断" | 冲突先请用户裁决，不自行取舍 |

## 规则分级与优先级

- **刚性（Rigid，必须执行）**：复述核对 / spec 版本递增 + 变更记录 / 受影响条目标记 / 冲突先裁决
- **弹性（Flexible，适配原则）**：变更访谈深度（以用户确定完成为准）/ 措辞方式
- **优先级链**：用户拍板 > 场景规则 > AI 建议

## 工程准则

- **副作用显式管理**：每次变更检查影响面——受影响规格条目/任务/文档全部显式更新或标注，不遗漏
- **先查证，不假设**：以现有文档（spec/plan/Progress）为准，拿不准先读再问
- **三次失败协议**：失败路径 ① 诊断修复 → ② 换方案（不重复同一操作）→ ③ 重新思考 → 3 次后求助用户
