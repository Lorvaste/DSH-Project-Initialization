# 《AI 产品创建对齐插件》想法思路（需求理解 v0.2 草案）

> 本文档由产品经理 + 技术经理双视角整理，基于多轮需求访谈 + plan.md 项目结构规范。
> 状态：**草案，待用户确认**。剩余待确认项见文末清单，确认后升级为 v1.0 冻结。

---

## 一、问题定义

### 1.1 用户痛点

使用 AI 从零开始创建产品时，**最终产物与最初想法不一致**。

### 1.2 根因诊断

传统软件工程靠「需求文档 → 设计评审 → 测试 → 验收」的显式对齐点防止偏差。
AI 辅助开发把这套纪律压缩成了「一句话想法 → 直接产出」，**对齐点全部消失**：

- 没有规格约束 AI 别理解偏（缺 SDD 纪律）
- 没有验收标准判断 AI 做对没有（缺 TDD 纪律）
- 隐式假设未表达：用户以为说清楚了，AI 只拿到几个词

### 1.3 偏差形态（用户实测，四类全覆盖）

| 类型 | 表现 |
|---|---|
| 功能层面 | 要 A 功能，做出来是 B 功能 |
| 细节层面 | 大方向对，参数/界面/边界条件不对 |
| 范围层面 | 做了没要的，或漏了明确要求的 |
| 实现层面 | 结果对，实现方法不是用户要的 |

### 1.4 产品核心洞察

> 插件卖的不是 AI 能力，是**对齐机制**：把隐式假设变成显式检查，让想法和产物之间每一步都有据可查、可追溯、可回滚。

## 二、产品定位

- **形态**：一个 DSH 插件（「场景模式」）
- **使用者**：开源给所有人（GitHub + DSH 插件市场双渠道分发）
- **覆盖产品类型**：三类场景——纯软件 / 纯实体 / 复合项目（软件+硬件组合）
- **交互方式**：混合式——访谈收集需求出规格（人对齐），执行阶段自动化（AI 干活）

### 2.1 「场景模式」设计（用户提出）

插件安装后提供「产品创建」专用场景：

1. **工具白名单**：只挂载必要工具，砍掉无关工具——每个工具定义都占上下文 token，工具越多 AI 有效思考空间越小
2. **内置 skill 规范**：访谈方法论、规格模板、提交规范
3. **编排模型**：流程状态机（第三章）
4. **打包为插件**：可分发、可安装、可进插件市场

### 2.2 场景「从零开始」功能定义（定案）

> 技术确认：DSH 官方 **agent preset** 机制（目录 + `agent.cordis.yml` 插件列表）即用户所说"场景模式"的原生实现——preset 决定会话的工具、提示词段落与 skill，会话产出内容前可选择/切换，放 `<dshHome>/.agent-presets`，GUI 原生管理（新建会话 chip/默认值/复制/删除）。

| 项 | 定案 |
|---|---|
| 实现载体 | DSH agent preset（官方机制）|
| preset id | `from-scratch`（kebab-case，符合 `[a-z0-9][a-z0-9-]*`）|
| 显示名 | **从零开始** |
| 会话结构 | 单会话 |
| **范围** | 工作区确认 → git init → ssh 远端（可选）→ 默认骨架 → 访谈（六步问答）→ 规格冻结 → spec 初版终稿 → **初稿任务拆分** → 文档推送 → **场景结束**；执行/验收交给后续其他会话 |
| 工具白名单 | 三族：`ask-user`（访谈提问，选项/多选 UI）+ `fs`（工作区读写）+ `bash`（git 操作）|
| skill 清单 | ① 脚手架 skill（默认骨架模板+占位符）② 访谈 skill（六步+五组准则，3.5）③ 冻结成档 skill（复述→逐条确认→spec.md）④ 任务拆分 skill（规格→任务清单初稿，标注规格条目映射）|
| 规则来源 | 其他骨架生成规则 → 项目 Rules.md 第四章（项目内优先）|
| 入口 | 新建会话选择 preset（原生 chip）|
| 权限 | 默认 workspace-write + ask；git push 遇沙箱拦截时引导权限升级（已知环境坑）|
| 终态产物 | 冻结 spec.md（Reference/）+ 任务拆分初稿 tasks.md（Reference/）+ 已推送的 git 仓库 |

### 2.3 分发与仓库结构（定案）

| 项 | 定案 |

## 三、流程设计（按 plan.md 规范）

### 3.1 进入路径一：项目刚开始（从零流程）

```
确认工作区 → git 初始化 → ssh 链接远端（可选，ssh 最稳定）
→ 初始化项目结构（通用骨架）并保存
→ 需求问答（访谈，确定类型/规模）
→ 生成类型子结构（软件/硬件，有则生成）
→ 整理统合需求 + 用户确认（规格冻结）
→ 结构化编写文档并保存推送
→ 任务分解 + 追溯（v1.1）
→ 执行（每步对照规格）
→ 验收（逐条对照，v1.1）
```

| 阶段 | 做什么 | 产出物 | 防什么偏差 |
|---|---|---|---|
| 工作区+git+ssh | 确认工作区、git init、ssh 远端（可选） | git 仓库 | 变更不可追踪 |
| 通用骨架 | 初始化 9 项共有结构并保存 | README/LICENSE/Rules/Structure/Progress/plan/Other/Reference/.git | 无地基 |
| 需求问答 | 结构化访谈（自适应深度），确定类型/规模 | 需求说明书 | 需求模糊、没说清楚 |
| 类型子结构 | 按类型生成软件/硬件子文件夹（有则生成） | Frontend/Backend/Database、Model/电路/嵌入式 | 结构错位 |
| 规格冻结 | **AI 复述完整需求 → 用户逐条确认 → 冻结** | 规格文档（四类规格） | AI 理解偏、隐式假设 |
| 文档推送 | 结构化编写文档并保存推送 | 远端同步 | 版本漂移 |
| 任务分解 | 规格拆任务，标注对应需求（v1.1） | 任务清单+追溯矩阵 | 漏功能、做多余功能 |
| 执行 | 每步对照规格检查（v1.1） | 检查记录 | 上下文漂移 |
| 验收 | 逐条对照规格（v1.1） | 验收报告 | 做完才发现不对 |

### 3.2 进入路径二：项目进行中（纠偏流程）

```
确认工作区 → 确认 git 状态与远端链接
→ 理解文档 + 用户核对理解（复述确认）
→ 结构化重排文档 → 用户确认完成 / 继续修正（循环）
→ 产物对照：AI 读取代码/文件，对照文档生成偏差清单（符合/偏离/缺失）
→ 用户确认 → 逐项修正
```

- 文档层对齐与产物层对照**都包含**（用户 2026-08 裁决）
- 与从零流程并行设计，执行优先级从零优先

### 3.3 规格文档结构（四类规格）

功能规格（做什么）/ 细节规格（参数、边界、界面）/ 范围声明（明确不做什么）/ 实现约束（怎么做）。

### 3.4 git 规范（全配齐）

- `git init` + 初始提交
- ssh 链接远端（用户可选；ssh 最稳定，https 需 token 管理）
- `.gitignore`、`README.md` 生成
- 提交规范（Conventional Commits：feat/fix/docs/chore/refactor 前缀）
- 每个里程碑文档保存并推送远端
- ⚠️ 环境事实：DSH 沙箱内 git push 的 ssh 管道会被拦截，需权限升级（插件需处理）

### 3.5 访谈机制与准则（定案，内化到场景模式）

> **归属**：访谈机制与准则**内化到场景模式（skill 指令）**，不写入项目 Rules.md。
> 规则分工：默认骨架 → skill 模板；其他骨架生成规则 → 项目 Rules.md 第四章；访谈规则 → 场景模式 skill。

**机制要点**
- 输入输出：一句话想法 → 问答 → 需求说明书 → 验证 → 确认成档 → Reference/spec.md
- 体量判定：AI 判定深度档位（浅/中/深），用户可纠正；档位只决定提问强度建议，**不设问题数上限**
- **问答逻辑（六步，用户定案）**：
  1. **想做什么**：用户自由描述想法 → AI 复述理解确认
  2. **功能实现范围**：功能清单（做什么）+ 边界（不做什么/排除项），含实现约束初确认
  3. **细则确认**：参数、边界条件、行为、异常处理（一次一问）
  4. **结构化拆分与确认**：按**用户理解的功能域**拆分（用户描述功能域划分 → 逐域确认，每域关联规格条目；任务粒度由用户决定，AI 只按域组织不规定粒度）
  5. **遍历性验证逻辑与遗漏并修复**：AI 遍历全部条目——逻辑自洽（条目间矛盾、条件不闭环）/ 覆盖完整性（四层缺口）/ 遗漏（边界、异常）→ 问题清单 → 用户确认 → 修复 → 复验（循环至无问题）
  6. **确认成档**：全部确认 → 生成规格文档 Reference/spec.md（冻结）
- 收敛：**以用户确定完成为准**——用户随时可结束（任一步）
- 提问粒度：**一次一个问题**
- 记录：全程保留 Other/（可回溯）
- 冻结：成档 = AI 结构化复述 → 用户逐条确认（已确认/待定/驳回）→ 驳回重澄清 → 全部确认后成档冻结
- 冻结后变更：显式记录，禁止静默漂移

**准则（五组）**
- 提问准则：一次一问；带选项/示例降低回答成本；不诱导（不预设答案）；不评判（专业错误就事论事纠正）
- 记录准则：每个回答显式记录，AI 随时可复述；隐式假设逼出（模糊词必须追问具体含义）；矛盾检测（前后冲突指出请裁决）
- 收敛准则：AI 不得为问而问；每步完成提示下一步，由用户决定继续或结束
- 冻结准则：复述必须是结构化理解；未确认条目不进规格；遍历验证未通过不成档
- 角色准则：AI 是引导者不是决策者；用户是唯一权威；全程可回溯

### 3.6 规格文档与任务拆分结构（定案）

**spec.md（Reference/spec.md，冻结后权威）**

```markdown
# spec.md — 项目规格（vX.Y 冻结）

## 元信息
项目名 / 场景类型（纯软件·纯实体·复合）/ 体量档位（浅·中·深）/
冻结版本 / 冻结日期 / 确认方式（AI 复述 + 用户逐条确认）

## 1. 项目概述（想做什么）
一句话定位 + 目标价值 + 核心用户/用途

## 2. 功能规格（做什么）
| ID | 功能 | 状态 |
（不设优先级；验收归场景外会话，spec 为纯需求描述）

## 3. 细节规格（参数·边界·界面）
| ID | 关联功能 | 细节 | 边界/异常 | 状态 |

## 4. 范围声明（不做什么）
| ID | 排除项 | 原因 | 状态 |

## 5. 实现约束（技术栈·偏好）
| ID | 约束 | 说明 | 状态 |

## 6. 变更记录
| 版本 | 日期 | 变更 | 原因 | 确认 |
```

- 条目编号：**F/D/R/I 前缀 + 序号**——全文档追溯锚点（遍历性验证/任务拆分/后续验收都按 ID 关联）
- spec 为**纯需求描述**（验收要点字段已移除，验收归场景外后续会话）
- 状态字段：冻结时全部为「已确认」；待定/驳回条目不进 spec
- 实体产品规格：**单独结构**，后续设计（v2）

**tasks.md（Reference/tasks.md，初稿任务拆分——按用户理解的功能域组织）**

```markdown
# tasks.md — 任务拆分（初稿）

## 元信息
关联规格版本：vX.Y

## 功能域（用户理解，问答④确认）
| 域 ID | 功能域 | 说明 | 关联规格条目 |
| MOD-01 | 用户管理 | 注册/登录/资料 | F-01, F-02, D-01 |

## 任务清单（按功能域组织）
### MOD-01 用户管理
| ID | 任务 | 关联规格 | 依赖 | 状态 |
| MOD-01-T01 | 注册表单 | F-01 | - | 待办 |
```

- **拆分原则**：按用户理解的功能域组织任务，不按固定细则机械拆分；任务粒度由用户决定（可粗可细）
- 域 ID：`MOD-xx`；任务 ID：`MOD-xx-Tyy`（域内编号，可追溯）
- 场景产出物之一（与 spec.md 分离，单独文件）
- 后续会话在此文件上细化执行

### 3.7 流程状态机（定案，场景「从零开始」）

**状态集合**（10 态 + 访谈子状态机）：

```
workspace → git-init → git-remote → scaffold → interview → freeze
→ spec-final → task-breakdown → docs-push → done
```

**转移与闸门**：

| # | 当前状态 | 闸门（校验通过才转移）| 下一状态 |
|---|---|---|---|
| 1 | 进入 | 用户确认工作区目录 | workspace |
| 2 | workspace | 目录有效可写 | git-init |
| 3 | git-init | `git init` 成功（或已存在）| git-remote |
| 4 | git-remote | 用户选择：ssh 链接 / **跳过**（可选）| scaffold |
| 5 | scaffold | 骨架 9+2 项文件齐全 | interview |
| 6 | interview | 六步完成：④功能域全确认、⑤遍历验证通过 | freeze |
| 7 | freeze | 复述逐条确认全通过（无待定/驳回）| spec-final |
| 8 | spec-final | spec.md 初版终稿写入 Reference/ | task-breakdown |
| 9 | task-breakdown | tasks.md 按功能域生成 | docs-push |
| 10 | docs-push | commit 成功（push 可选，沙箱拦截引导升级）| done |
| 11 | done | 交付总结（终态）| - |

**访谈子状态机**（interview 内部）：

```
idea → scope → detail → domain-split → verify → confirm
```

- 每步闸门：本步信息已显式记录（detail 后四层覆盖自检）
- verify：问题清单 → 修复 → 复验循环（无问题才出）
- confirm：AI 复述 → 逐条确认 → 全确认才进入 freeze

**设计原则（定案）**：
- **闸门策略**：校验失败回本步重做，除非用户明确要求跳过（跳过需显式记录）
- **回退**：任意状态可回退到之前任意状态（全程可回溯准则落地）
- **状态记录**：当前状态写入 Progress.md（会话中断可恢复续跑）

按类型与功能块拆分组合（软件子结构 + 硬件子结构）。

## 五、双模板设计

### 5.1 软件产品模板

- 问答逻辑：六步流程（想做什么 → 功能实现范围 → 细则确认 → 结构化拆分与确认 → 遍历性验证 → 确认成档），见 3.5
- 验收：TDD 式验收清单（先定验收标准，再实现）

### 5.2 实体产品模板

- 独立问答流程 + 独立验收方式（与软件分开）
- 硬件子结构按 plan.md「有则生成」执行
- 实体验收机制：**不在插件范围**（已移出插件需求，场景外处理）

### 5.3 访谈深度（体量判定决定提问强度，不设问题数上限）

| 体量 | 示例 | 提问强度 |
|---|---|---|
| 小工具 | 单文件、几百行脚本 | 浅：每层 1-2 问 |
| 中等项目 | 多文件、多模块、有界面 | 中：每层多问分支 |
| 完整应用 | 前后端、数据库、部署 | 深：多轮多分支 |

## 七、技术方案（技术经理视角）

- **实现载体**：DSH 插件（Cordis 框架 + TS），本质是「场景配置 + 技能规范 + 模板库 + 流程状态机」，不写重代码
- **规则内化分工**：默认骨架 → skill 模板；其他骨架生成规则 → 项目 Rules.md 第四章；访谈机制与准则 → 场景模式 skill 指令（见 3.5）
- **工具白名单**：访谈阶段最小集（文件读写为主）；执行阶段按需挂载
- **流程状态机**：两条路径的状态流转，每步有输入校验，不满足不进下一步
- **追溯矩阵**：需求条目 ↔ 任务 ↔ 产物 ↔ 验收项 映射，防漂移核心数据结构
- **双通道检查**：产物 vs 规格，AI 自动初检 + 人工确认终检
- **脚手架生成器（模板化方案已定案）**：
  - **默认骨架**：skill 内置 templates/ 模板直接产出（含 `{{PROJECT_NAME}}`/`{{REMOTE_URL}}`/`{{AUTHOR_NAME}}` 占位符，生成时替换），规则固化在 skill 内
  - **其他骨架**：skill 读取项目 Rules.md 第四章，按 4.1 场景判定 → 4.2（软件）/4.3（实体）/4.4（复合）对应规则生成
  - **规则源**：项目 Rules.md 即为规则源（第四章）
  - **项目内优先**：生成后用户可修改 Rules.md，skill 下次运行以项目内文件为准，不覆盖用户修改
- **分发**：GitHub 开源仓库 + DSH 插件市场
